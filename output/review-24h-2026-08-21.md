## Confirmed findings — detail

### 1. History keyboard activation double-fires Restore/Send — HIGH
**File:** `loopmaster/loopmaster-app/static/prompt_builder.js:1045`

`historyViewport` has both a click listener (line 1044) and an Enter/Space keydown listener (lines 1045–1047) that call `handleHistoryClick`. History rows contain native `<button>` elements (lines 849–857). When focus is on a Restore/Send/Delete button, pressing Enter runs `handleHistoryClick` from the keydown handler AND the browser's native button activation dispatches a click that bubbles to the click listener. `restore()` runs twice; `onResend()` (`submitCurrentGeneration`) fires twice, submitting two identical generation jobs to `/api/generate` and creating two pending history entries. Space double-fires the same way, and because the keydown handler never calls `preventDefault`, Space on a focused row also scrolls the viewport.

**Fix:** in the keydown handler, return early when `event.target.closest('button')` (let native click activation handle it), and call `event.preventDefault()` when handling Enter/Space on the row itself.

### 2. No concurrency guard on generation; resend and slicer presets bypass the disabled button — HIGH
**File:** `loopmaster/loopmaster-app/static/app.js:7350`

Only the `btnGenerate` click path is protected (a disabled button swallows `.click()`). `promptBuilder.setOnResend(() => submitCurrentGeneration())` at line 7108 and the slicer preset buttons at line 7346 call `submitCurrentGeneration()` directly, and neither `submitCurrentGeneration` (line 7086) nor `runGeneration` (line 7350) checks whether a generation is already running. Compare `runOutpaint` at line 7487, which has the exact guard: `if (btnGenerate.disabled) return;`. Clicking Send in the history panel (or a slicer preset) while a generation is in flight starts a second concurrent job: `setGenerationCancelState` is overwritten (Cancel now targets the wrong job), and the first job's `finally` block re-enables `btnGenerate` while the second is still running. Combined with finding 1, one Enter press on history Send can launch two jobs at once.

**Fix (owner-corrected):** use a real generation mutex — a module-level `generationInFlight` flag acquired at the very start of `submitCurrentGeneration` / `runGeneration`, **before** the pending history entry is created, and released in the `finally`. Do NOT rely on checking `btnGenerate.disabled` inside `runGeneration()`: by then the pending history entry already exists, and the button state is a UI side effect, not a lock. All entry points (Generate button, history resend, slicer presets) must go through the same mutex.

### 3. Typing in the prompt textarea before config loads throws on every keystroke — MEDIUM
**File:** `loopmaster/loopmaster-app/static/prompt_builder.js:159`

`config` is `null` (line 83) until `initialize()`'s fetches complete at line 959 — and stays `null` forever if any of the 9 option fetches fails (the catch at line 1011 leaves it null). `sectionKeys()` dereferences `config.sections` with no guard (line 160). The `#prompt-freeform` input listener attaches synchronously (line 1021) before `initialize()` runs (line 1050), and the textarea is enabled in `index.html:50`. Typing during the fetch window runs `queueFreeformUpdate → commit → selectionState → sectionKeys() → TypeError: Cannot read properties of null (reading 'sections')` on every keystroke; the manual prompt is never persisted. The history-click path is live pre-init too (`renderHistory()` at line 1049), so Restore/Send on a history row before init completes hits the same crash. `randomizeAll` already guards with `if (!config) return`; `commit`/`sectionKeys` do not.

**Fix (owner-corrected):** do NOT make `commit()` a silent no-op — that stops the crash but silently loses what the user typed. Preserve or buffer input instead: keep the raw freeform text in a pre-init buffer (or leave it in the textarea and skip only the derived-state work), then replay/commit it once `initialize()` resolves. For the history path, either defer `renderHistory()` until init resolves or queue the clicked action and run it after `ready`.

### 5. api_regenerate hardcodes 4 variants while api_generate allows up to 8 — MEDIUM

### 8. Hardcoded chunk_size=64 with default overlap=32 doubles VAE decode compute — MEDIUM (perf, UNPROVEN — benchmark first)
**File:** `stable-audio-3/stable_audio_3/inference/sampling.py:388`

`pretransform.decode` is called with `chunk_size=64` while `decode_audio`'s default `overlap` stays 32 (`autoencoders.py:596`), so hop = 32 and every latent is decoded twice — overhead factor `chunk/(chunk-overlap)` = 2.0×, versus 1.33× at the default `chunk_size=128`. The 64 value was chosen as a fixed worst case for 12 GB cards, but the code already queries `torch.cuda.mem_get_info` at `sampling.py:578`. On cards with headroom this is roughly a 1.5× VAE decode speedup with perceptually equivalent output (not bit-identical across chunk sizes; the overlap-trim math is chunk-size independent).

**Fix (owner-corrected):** this is a *plausible* improvement, not a proven win. Before changing anything, benchmark on the 12 GB GPU: decode wall-clock at chunk 64 vs 128, peak VRAM per configuration, output equivalence (audible/statistical, since results are not bit-identical), and the OOM fallback path. Only then wire an adaptive chunk size off the existing `mem_get_info` query, keeping 64 as the guaranteed-safe floor.

### 9. Preallocated decoded batch lives on GPU; CPU allocation would free decode headroom — MEDIUM (perf, UNPROVEN — benchmark first)
**File:** `stable-audio-3/stable_audio_3/inference/sampling.py:395`

`decoded_batch = decoded.new_empty(...)` inherits the CUDA device, so the full decoded audio batch (B × 2ch × ~5.3M samples) stays in VRAM through decode (~85 MB fp16 for B=4), and `model.py:510-511` then materializes an fp32 GPU copy (~170 MB more). The only consumer (`generation_executor.py:410-412`) immediately moves the result to CPU fp32 — the GPU residency is pure waste of exactly the headroom the commit's `empty_cache` guard (sampling.py:577–580) protects. Caveat found during verification: `sampling.py:618-625` multiplies the decoded batch by a GPU-derived `audio_mask` (`padding_mask` is non-None since `model.py` passes `mask_padding_attention=True`), so the mask must be applied per-variant or moved to CPU as part of the fix.

**Fix (owner-corrected):** plausible, not proven. Benchmark on the 12 GB GPU first: peak VRAM with GPU-resident vs pinned-CPU `decoded_batch`, end-to-end decode time (pinned-host copies are not free), output equivalence, and behavior under the OOM fallback. If the win holds, allocate `decoded_batch` with `torch.empty(shape, dtype=decoded.dtype, device="cpu", pin_memory=True)` + per-variant `copy_(decoded, non_blocking=True)`, and handle the `audio_mask` device mismatch (apply mask per-variant on GPU before copying, or move the mask).

### 10. Each published WAV is fully re-read twice after being written — MEDIUM (perf)
**File:** `loopmaster/loopmaster-app/app_server.py:575`

`_save_variant_atomically` writes the WAV via `torchaudio.save`, then `acidize_wav_file` reads the entire file and rewrites it (`wav_metadata.py:282-283`, `377-378`), then `finalize_sidecar_for_wav` re-reads the entire rewritten file a third time to compute SHA-256 (`asset_contract.py:566-571`, `_sha256_file` at 825). Per variant: 2 full writes + 2 redundant full reads (~11.5 MB each for a 60 s 48 kHz stereo PCM16 file), × up to 8 variants per job. `acidize_wav_file` already holds the final bytes as `new_content` in memory when it writes.

**Fix:** have `acidize_wav_file` also return `{"sha256": hashlib.sha256(new_content).hexdigest(), "bytes": len(new_content)}`, and add an optional precomputed-digest/size parameter to `finalize_sidecar_for_wav` so `app_server.py` passes those instead of re-reading the file.

### 11. 1 Hz status poll re-serializes the full asset/progression echo every tick — LOW (perf)
**File:** `loopmaster/loopmaster-app/app_server.py:1178`

Simplest safe shape: return the slim dynamic set while the job is queued/running, and the full record once the job is terminal.

### 15. Phantom "queued" job leaks if anything between register and submit throws — LOW
**File:** `loopmaster/loopmaster-app/app_server.py:917` (also `api_regenerate` ~1146)

In `api_generate` the job is registered as `queued` and durably recorded at line 872 before `GenerationTask` construction (889–925), but only `GenerationQueueFull` is caught around `generation_queue.submit` (926–929). `ProgressionProvenance.from_resolution` (917–921) can raise `ValueError`/`KeyError`/`TypeError`, and `submit` raises `RuntimeError('generation queue is stopping')` during shutdown — both escape uncaught, returning 500 while the registered job stays `queued` forever: never terminal, never pruned by `_prune_terminal_jobs`, reported by `/api/status` with position null until a restart mislabels it `interrupted`. ### 16. Fanout timeout retry can delete the other attempt's freshly published WAV — LOW
**File:** `loopmaster/loopmaster-app/app_server.py:602`

`generation_executor.py:701-707` runs `publish_one` through `run_parallel_fanout` with `timeout_seconds=30.0, retries=2`. `fanout._call_with_timeout` (fanout.py:23–63) abandons a timed-out attempt in a daemon thread that keeps running while the retry starts; its docstring explicitly requires idempotent adapters. `_save_variant_atomically` is not idempotent under that overlap: both attempts target the same final paths with no per-path lock, and the cleanup at lines 602–608 does `os.remove(file_path)` whenever the attempt published the WAV but not the sidecar. Reachable interleaving: abandoned attempt-1 replaces the WAV → attempt-2 replaces it again → attempt-1's sidecar `os.replace` raises (it lacks the Windows `PermissionError` retry the WAV replace has at 578–588) → attempt-1's `finally` deletes attempt-2's WAV → attempt-2 publishes its sidecar. Result: an orphaned sidecar with no adjacent WAV — the exact half-published state the contract tells consumers to reject — while fanout reports `ok=True`. Low likelihood (needs a >30 s local publish plus a sidecar replace failure), real mechanism.

**Fix (owner-corrected):** prefer `timeout_seconds=None` for local file publication — with no timeout there is no abandoned attempt, so overlap cannot happen at all. A per-path lock alone is NOT sufficient: an abandoned daemon-thread attempt still holds or re-acquires the lock at unpredictable times and can interleave its cleanup with a later retry. Also give the sidecar `os.replace` the same Windows `PermissionError` retry the WAV replace has.

All dynamic positioning routes through typed `attr()` (`attr(data-progress type(<number>), 0)` etc.), which requires Chromium 133+ and is unsupported in Firefox and Safari. A verify agent refuted this as "Electron-only, QA guards the floor" — but LoopMaster explicitly supports normal browser launching (`run_server.bat` serves the app to any browser), so the Electron QA guard (`qa/frontend-qa.js:756-766`) cannot establish the compatibility floor. In a non-supporting browser every card playhead, progress fill, arranger playhead line, and rotation indicator silently falls back to 0/auto and never moves, while `setPresentation` (`app.js:158`) keeps writing attributes that do nothing.

**Fix:** either (a) provide a JS fallback: feature-detect `CSS.supports('width', 'calc(attr(data-progress type(<number>),0) * 100%)')` once at startup and, when unsupported, have `setPresentation` write inline `style.transform`/`style.width` directly instead of data attributes; or (b) declare and enforce a Chromium-133+ floor for browser launches too (detect and show an unsupported-browser banner). Option (a) preserves the stated browser support; recommended.

## Refuted findings (checked and rejected — 3 stand)

Recorded so they are not re-raised later. Two other refutations (cKUP chordTrack, typed `attr()`) were overturned on owner review and moved above as findings 20–21.

1. **"`_next_variation` walks the entire session tree once per variant" (`generation_executor.py:574`)** — deliberate: asset filenames carry no track number, so the take counter must be session-wide to prevent collisions in flattened pack exports (docstring at line 570). Cost is milliseconds against a few-hundred-file tree.
2. **"Generate request blocks on an fsync'd full-history rewrite" (`app_server.py:678`)** — deliberate durability contract: the queued record must be durable before the client sees 202 so a crash converts it to a terminal interrupted-error instead of silently losing an accepted job (`job_history.py` docstrings). Tens of ms gating a multi-minute GPU job is not a meaningful win; the proposed fix trades away intended crash safety.
3. **"Batch the per-variant VAE decode loop for GPU utilization" (`sampling.py:384`)** — the "free win" math fails in this codebase: halving chunk_size to compensate for batch memory makes hop ≤ 0 and raises `ValueError` (`autoencoders.py:614-617`); `decode_audio` silently bypasses chunking when latents are shorter than chunk_size (line 608), risking a B× VRAM spike against the pinned 12 GB budget (`model.py:259`); and the sequential form is a tested peak-VRAM design (`tests/test_runtime_memory.py:70`) that feeds the per-variant progress callback. Any batching would need an overlap-aware redesign gated on measured headroom.
